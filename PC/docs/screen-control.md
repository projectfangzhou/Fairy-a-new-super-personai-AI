# 屏幕操作：暂停/继续/停止与平台门控

清单第五节前两条：屏幕操作要有明显的暂停、继续、停止，且暂停在当前原子操作完成后、下一动作前生效、
停止后不得继续执行；Linux 只在验证过的会话上开放，不支持时禁用并说明原因。

## 一、语义（这是本节的重点）

`ScreenSession` 是一个纯状态机，没有句柄、不看时钟，所以它的行为可以直接断言：

| 动作 | 发生了什么 |
|---|---|
| 空闲时暂停 | 立刻进入 `Paused`，下一个动作被拒 |
| 动作进行中暂停 | 状态仍是 `Running`，但记下"暂停待生效"；**当前动作照常做完**，做完的那一刻转 `Paused`，下个动作被拒 |
| 继续 | 回到 `Running` 并清掉待生效标记 |
| 停止 | 立刻 `Stopped`；正在飞的那个动作允许做完，之后一律不执行 |
| 停止后继续 | **不恢复**。`Resume` 返回 `Stopped`，"停止"不是"暂停到有人点继续" |

最后一条是刻意的：如果停止能被继续救回来，那"停止"就只是另一种暂停，用户按下去等于没有止损。

## 二、单一入口

原来 6 个屏幕工具各自持有 `IScreenControlService`，谁都能直接点鼠标。现在它们只持有
`ScreenActionRunner`，动作按固定顺序过四道：

```
平台可用? → 会话允许? → 用户批准? → 执行 → 告诉会话做完了（暂停在这里落地）
```

- **平台不可用**：直接拒绝并说明原因，**不会弹审批**——没意义的确认只会让人对确认麻木。
- **会话暂停/停止**：直接拒绝，同样不弹审批。
- **审批**：走 `ApprovalGate`，风险类别是新增的 `RiskCategory.OperateScreenAndInput`（追加在枚举末尾，历史审计含义不变）。没有审批界面时按失败关闭拒绝，不会默认放行。
- **审计**：每次尝试都记一条，含类别、摘要、目标与决策结果。
- **输入内容不进审计**：`type_text` 只记"输入 N 个字符"，因为那可能是密码。

## 三、平台门控

`ScreenControlAvailability`：Windows 支持；Linux **一律禁用并给出原因**（"尚未在 Ubuntu 22.04/24.04、Debian 12 的 X11/Wayland 会话上验证"），并在平台字段里带上实际探测到的 `XDG_SESSION_TYPE` / `XDG_CURRENT_DESKTOP`；其他平台同样禁用并说明。这就是清单要的"不支持时禁用并说明原因"，而不是逐个动作失败。

要开放 Linux，前提是在目标发行版上真的跑过——这件事我在这台 Windows 上做不到，所以按未验证处理。

## 四、界面与接口

控制中心新增「屏幕操作」区块：状态行 + 暂停/继续/停止三个按钮，并显示平台、在飞动作数、已完成、
被拒次数和最近一次拒绝的原因。

| 接口 | 作用 |
|---|---|
| `GET /api/screen` | 状态、计数、平台判定与不支持原因 |
| `POST /api/screen/pause` | 暂停（动作中则回"当前动作做完后生效"） |
| `POST /api/screen/resume` | 继续（已停止则 409） |
| `POST /api/screen/stop` | 停止 |

## 五、验证

`Tests/ScreenSession` 58 项、`Tests/Dashboard` 247 项（+17），PC 端 27 套合计 1623 项断言全过；页面
15 个 `<section>` 配平、内嵌 JS 过 `node --check`。

覆盖的关键行为：暂停/停止期间**一个动作都没到服务层**（用假实现记录调用次数断言）；动作中暂停不会
中断当前动作、只拦下一个；停止后继续无效；审批被拒/无审批界面/取消都不执行且会话不残留"在飞"；
平台不支持时**不弹审批**；每次尝试都进审计且类别正确；界面上停止后按继续返回 409 且状态仍是停止。

## 六、没做的

1. **Windows-MCP 受控后端没接**。这是清单第五条的下一条：把 MCP 当可选感知/操作后端，同样过审批、
   暂停/停止与审计。顺带说清楚一件事：现有的 `Services/MCPClient.cs` **不是 MCP 协议**——它自己发明
   了 `/tools`、`/call`、`/connect` 三个 HTTP 端点，而 MCP 是 JSON-RPC 2.0（`initialize`、
   `tools/list`、`tools/call`，stdio 或 SSE 传输）。要用它就得先有真客户端，这是下一步。
2. **没有跑过一次"让 agent 真的点鼠标"的会话**。上面所有断言都是单元层面：门控、审批、状态机、
   审计。真实桌面上的端到端操作（含暂停在两次点击之间生效）需要你在机器上跑一次。
3. **Linux/Android 的屏幕操作没有实现**：Linux 按未验证禁用；Android Shizuku 属于里程碑第 5 条。
